# Database engineering

## Activation criteria
Database Engineer tasks; Backend/AI engineers when touching persistence; reviewers judging migrations.

## Required inputs
Data model spec (architecture.json `data_models`), access patterns from requirements/contracts, chosen DB + ORM/migration tool, retention/privacy requirements.

## Decision tree
- Relational data with relations/transactions → PostgreSQL (default) / MySQL / SQL Server per stack; single-user or prototype → SQLite.
- Document-shaped, schema-flexible data with no cross-document transactions → MongoDB (only if requested/justified).
- Cache/ephemeral counters → Redis only with a requirement (rate limiting at scale, sessions across instances).
- Semantic search over text → pgvector inside PostgreSQL when Postgres is already used; a separate vector DB only with scale justification.

## Schema design
- Primary keys: UUID (v7 preferred when available) or bigint identity; consistent naming (`snake_case`, plural tables or per project convention).
- Constraints in the database: NOT NULL, UNIQUE, CHECK, FOREIGN KEY with explicit `ON DELETE` (RESTRICT by default; CASCADE only for owned children).
- Types: timestamps `timestamptz` in UTC; money as `numeric(…)`/integer minor units; enums as check constraints or lookup tables; JSONB only for genuinely unstructured data.
- Indexes: every FK; columns in frequent WHERE/ORDER BY; composite indexes in selectivity order; partial indexes for soft-delete; avoid redundant indexes.
- Multi-tenant/user data: `owner_id`/`tenant_id` columns indexed and used in every query (consider Row Level Security in Postgres).
- pgvector: `vector(<dim>)` column with recorded embedding model + dimension in a metadata table; HNSW or IVFFlat index with the distance operator matching the model (cosine `vector_cosine_ops`).

## Migrations
- One migration per logical change, generated by the tool then reviewed by hand; deterministic and idempotent with respect to the tool's history table.
- Provide `downgrade`/rollback where the tool supports it; otherwise document a recovery path.
- Expand → migrate → contract for changes to existing data (add nullable column, backfill, then add constraint); never drop columns/tables in an existing project without approval.
- Tools: Alembic (`alembic revision --autogenerate`, review, `alembic upgrade head`), Prisma (`prisma migrate dev` locally, `prisma migrate deploy` in CI; never `migrate reset` on shared DBs), Drizzle (`drizzle-kit generate` + migrate), EF Core (`dotnet ef migrations add`), Flyway/Liquibase (versioned files).

## Seeds and test databases
Deterministic seed data with fake values (no real PII); separate dev seed from test fixtures. Tests run against an isolated database: SQLite temp file, a docker container named `devpipeline-<run>-db` that you stop afterwards, or Testcontainers. Never point tests at an existing or production database.

## Queries
EXPLAIN (ANALYZE in test DB) hot queries; eliminate N+1 with joins/eager loading; paginate; select only needed columns; transactions around multi-statement writes with the right isolation level; use `SELECT … FOR UPDATE` or optimistic locking for concurrent updates.

## Anti-patterns
Float for money; missing FKs "for flexibility"; storing comma-separated lists; unbounded queries; migrations that depend on application code; destructive migrations without approval; ORM lazy loading in loops.

## Validation
Apply all migrations to an empty test DB (and downgrade one step where supported), load seeds, run repository/integration tests; record logs and exit codes.

## Completion criteria
Schema enforces the data rules, migrations apply cleanly from zero, rollback/recovery documented, seeds deterministic, queries indexed, tests pass.
